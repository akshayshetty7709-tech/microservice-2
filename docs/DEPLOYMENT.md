# Locate360 — Deployment Documentation

## Architecture
- **Infra (Terraform):** VPC, 2 public subnets, 1 K8s master EC2, 2 K8s worker EC2,
  S3 bucket + CloudFront for the React frontend.
- **Cluster config (Ansible):** Docker, containerd, kubeadm/kubelet/kubectl,
  cluster init, worker join, NGINX Ingress — zero manual SSH.
- **Services:** 22 Node.js microservices, each in its own Git repo, plus a
  separate frontend repo (23 repos total). The pipeline clones every repo
  into `repos/<name>` on the Jenkins agent, then injects **one shared**
  multi-stage Dockerfile template (`docker/Dockerfile.template`) into each
  checkout before building — the template is not copied into each repo by
  hand, it's applied by Jenkins at build time, so all 22 stay in sync
  automatically whenever the template changes. Each repo owns only its own
  `src/`, `package.json`, and tests. One shared parameterized Helm chart
  with per-service values files handles deployment the same way.
- **Registry:** Harbor at `harbor.company.internal/locate360/<service>:<tag>`.
- **Secrets:** Vault only — Mongo URI, JWT secret, Redis URL, Kafka creds,
  injected into Jenkins env vars at deploy time and base64-encoded into a
  Kubernetes Secret via `helm --set-string`. Never in git, Dockerfiles, or
  Helm values files.
- **Monitoring:** kube-prometheus-stack scrapes node, pod, and per-service
  metrics (annotated pods); Grafana dashboard (`locate360-dashboard.json`)
  visualizes cluster/node/pod health, CPU, memory, request rate, error rate,
  and top-5 services by traffic.
- **CI/CD:** One Jenkinsfile chains every stage: Terraform → Ansible →
  Docker build → SonarQube + Quality Gate → Harbor push → Vault secret
  retrieval → Helm deploy → Prometheus/Grafana → frontend build → S3 sync →
  CloudFront invalidation.

## One-time setup in Jenkins
1. **Credentials store** — add:
   - `harbor-registry-creds` (username/password)
   - `vault-approle` (Vault AppRole role_id/secret_id)
   - `aws-locate360` (AWS access key/secret — used only by the pipeline, no
     console access needed)
   - `locate360-kubeconfig` (secret file, generated by the k8s-master
     Ansible role and pulled from the master node once, then rotated via
     Vault/Jenkins — not manually re-copied per run)
2. **Plugins** — HashiCorp Vault, SonarQube Scanner, Kubernetes CLI,
   Pipeline: AWS Steps, Pipeline Utility Steps, Git.
   - `git-locate360-creds` — SSH key or token with read access to all 22
     service repos plus the frontend repo.
3. **Jenkinsfile** — point a Multibranch/Pipeline job at
   `jenkins/Jenkinsfile` in this repo.

## Running it
- First run: check `RUN_TERRAFORM` and `RUN_ANSIBLE` to provision and
  configure the cluster.
- Subsequent runs (code changes only): leave both unchecked — the pipeline
  skips infra/config and goes straight to build → push → deploy.
- `IMAGE_TAG` defaults to the Jenkins build number; override for explicit
  versioning (matches the `service:1.0.0` Harbor convention).

## Adding a 23rd service
1. Create the new repo (no Dockerfile needed in the repo itself — Jenkins
   injects the shared template at build time).
2. Add `<name>: 'git@company-git:locate360/<name>.git'` to the `SERVICES`
   map in `jenkins/Jenkinsfile`.
3. Add `helm/values/<name>.yaml` (copy `user-service.yaml`, change
   `nameOverride`, `image.repository`, `ingress.host`, `vault.path`).
4. Create the matching Vault path (`secret/data/locate360/<name>`).
5. Grant `git-locate360-creds` read access to the new repo.

## Verifying the outcome
- `kubectl get pods -A` — all services Running, HPA active.
- `kubectl get ingress -A` — routes resolve through NGINX Ingress.
- CloudFront URL serves the built React frontend.
- Grafana dashboard shows live CPU/memory/request/error data for all 18
  services; Prometheus targets page shows all as `UP`.
